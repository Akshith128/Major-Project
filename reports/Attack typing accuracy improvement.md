# Let a classifier name attacks, LLMs explain

The fastest way to push AEGIS attack typing above 62% is not a better prompt or a bigger model. It is to stop forcing an answer the system cannot know, and to give a calibrated classifier better evidence. Of the 68 caught attack windows, **12 (4 Botnet, 8 SSH brute force) had no same-family example anywhere in the leave-day-out reference set**. That caps any closed-set method at **56/68 = 82%**. The current kNN already gets **42 of those 56 answerable windows (75%) right**. The local LLM adds nothing on top. Its confusions are identical to kNN's except for **5 extra errors** (DoS Hulk → DDoS), and it fixed none. Two more things change how the 62% should be read. A trivial "always DDoS" answer scores **68%**, because DDoS is 46 of the 68 windows. And the families that get confused are separated by features AEGIS never reads, while two of its 14 features fingerprint the testbed's TCP stack rather than the attack. The recommended design is a Random Forest plus distance-weighted kNN soft vote on shortcut-free behavioural window statistics, with an explicit "Unknown" answer calibrated on held-out days. The LLM then explains that verdict under an Ollama JSON schema and never picks the label. Score it with open-set accuracy, macro-F1, per-family confusion, abstention rate and paired McNemar tests, on fresh seeds frozen before anyone looks. Nobody has measured the gain yet. A realistic target is open-set accuracy in the 70–85% range with known-family accuracy near 85%. That is an inference from the error breakdown, not a result.

## Twelve of 68 errors were unanswerable before any model ran

The measured confusions explain most of the gap. Table 1 splits the seed-0 hybrid run by true label. The 68 caught attack windows were 46 DDoS (17 HOIC, 29 LOIC-HTTP), 10 DoS (8 Hulk, 2 GoldenEye), 8 SSH brute force and 4 Botnet. No Web Attack window reached the ≥50%-attack threshold, so the test effectively had four families ([benchmark-hybrid-same-network-nollm.json](benchmark-hybrid-same-network-nollm.json); [benchmark-hybrid-same-network-ollama.json](benchmark-hybrid-same-network-ollama.json)).

|---|---|---|---|---|
| Bot (02-03) | 4 | DDoS ×4 | DDoS ×4 | **Structural**: no Botnet reference when this day is held out |
| SSH-Bruteforce (14-02) | 8 | DoS ×8 | DoS ×8 | **Structural**: no Brute Force reference |
| LOIC-HTTP (20-02) | 29 | DDoS 21, DoS 8 | same | Learnable, possibly label noise |

| GoldenEye (15-02) | 2 | DoS 2 | DoS 2 | — |

*Table 1. Per-window naming on the same 68 windows. Accuracy: kNN 42/68 (62%), LLM 37/68 (54%).*

Three conclusions follow. First, the **structural ceiling is 82%** for any method that must name a known family. On the TCP-window ablation run, 11 Botnet windows were caught and the ceiling falls to 56/75. kNN again got 42 right there, so it still answers 75% of the answerable windows correctly ([hybrid-evaluation.md](hybrid-evaluation.md)). Second, the **LLM is a correlated, weaker copy of the retrieval vote**. On the windows where they differ, kNN was right 5 times and the LLM 0 times (exact McNemar p = 0.0625). That fits the literature: small zero-shot LLMs sit near chance on flow features. Qwen2.5-3B scored 0.455 accuracy on binary UNSW-NB15 against 0.95 for XGBoost ([arXiv 2510.17883](https://arxiv.org/html/2510.17883v1)). Fine-tuned 1B models only tie a Random Forest (F1 0.712 vs 0.716) ([arXiv 2601.15269](https://arxiv.org/abs/2601.15269)). Third, plain accuracy flatters the wrong systems. "Always DDoS" scores 68% but has a four-family **macro-F1 of 0.20**, against **0.33 for kNN and 0.25 for the LLM**. Accuracy alone would rank the trivial baseline first.

Leave-day-out is harder than it sounds, because each day-file holds one or two tools. The test is really **leave-tool-out**. LOIC-HTTP windows (20-02) can only be matched against HOIC as their DDoS example, so 8 of them landed nearer to Hulk. The few-shot literature shows the same drop: kNN falls from 93–97% in-domain to **about 84%** when trained on CIC-IDS2017 and tested on 2018 ([PMC12221178](https://pmc.ncbi.nlm.nih.gov/articles/PMC12221178/)). Cross-dataset MCC on CIC data collapses from about 96% to 26–44% ([arXiv 2402.10974](https://arxiv.org/html/2402.10974)). DoS against DDoS is partly irreducible here. The real difference between them is how many sources send the traffic, and the parquet has no source IPs.

Label noise adds a further ceiling. On 20-02, LOIC-UDP ran alongside LOIC-HTTP, but every flow was labelled HTTP. That is the same day that produced all 8 LOIC-HTTP → DoS errors. About a quarter of GoldenEye flows are attacker-RST artefacts, and zero-payload Hulk and SSH flows are "Attempted" rather than real attacks ([DistriNet CSE-CIC-IDS2018](https://intrusion-detection.distrinet-research.be/CNS2022/CSECICIDS2018.html)). Flood et al. find that CIC-18 DoS was launched against static targets, which produces millions of near-identical flows ([Flood et al. 2024](https://detlearsom.github.io/pubs/BadSmells-EuroSP24-finaldraft.pdf)). Cantone et al. count only **56 unique instances among 105,550 Slowhttptest samples** ([arXiv 2402.10974](https://arxiv.org/html/2402.10974)). One housekeeping fix belongs here too. `aegis/data.py` attaches the LOIC-UDP-labelled-as-HTTP caution to `DDoS2` (21-02), but DistriNet documents it on 20-02, which is `DDoS1`.

The retrieval itself was built for detection, not naming. `anomaly.evidence()` measures Euclidean distance after a `StandardScaler` fitted on **benign** windows. Features that barely vary in normal traffic therefore dominate the distance between two attacks. Two of the 14 features also carry the Init Fwd Win Bytes shortcut: `dominant_signature_share` includes it in the signature tuple, and `unique_tcp_window_ratio` is computed from it. A single-feature Random Forest on Init Fwd Win Bytes detects DoS Hulk almost perfectly on CIC-18, yet misclassifies every Hulk flow on CIC-17 ([Flood et al. 2024](https://detlearsom.github.io/pubs/BadSmells-EuroSP24-finaldraft.pdf)). Finally, with n = 68 every figure carries roughly **±12 points** of 95% uncertainty. The 8-point gap between 54% and 62% is not significant on its own.

## Behavioural statistics separate the families AEGIS confuses

The dataset authors' own per-attack feature ranking puts the confused families on features AEGIS never loads. For DoS Hulk and DDoS the top feature is **Bwd Packet Length Std**. For slow DoS it is **Flow IAT and Active/Idle time**. For Bot and Infiltration it is **forward payload volume** (Subflow Fwd Bytes / Total Len Fwd Packets) ([Sharafaldin et al. 2018](https://www.scitepress.org/papers/2018/66398/66398.pdf)). Brute force, by contrast, was "best" traced by Init Win bytes, which is exactly the artefact. Once that is removed, brute force has the weakest behavioural signature, and that fits the Brute Force → DoS confusion. Its real signature is a login dialogue: many medium-length TCP sessions with balanced forward and backward packet counts, small bidirectional payloads, a high PSH share and low variation between flows. HTTP floods instead show many short flows with a small fixed request, and the CIC-18 FTP "brute force" is mostly SYN → RST,ACK to a closed port ([DistriNet](https://intrusion-detection.distrinet-research.be/CNS2022/CSECICIDS2018.html)).

All of the needed columns are already in the ~78-column parquet. The recommended window statistics follow the artefact literature and Kitsune-style multi-flow aggregation ([arXiv 1802.09089](https://arxiv.org/pdf/1802.09089)), adapted for heavy-tailed CICFlowMeter values. Take `log1p` of rates, sizes and times. Use **median and 90th percentile** instead of means, because one long Slowloris flow or one big download dominates a mean. Add the **coefficient of variation** of forward packets, forward bytes and duration, which captures how repetitive the tool is. Add **share features**: zero-payload flows (marking "Attempted" or closed-port traffic), long flows (>10 s; avoid the 120 s CICFlowMeter timeout itself), RST, PSH and ACK. Add the window-level **backward/forward byte ratio**, which separates floods, downloads and login exchanges. And add **other-protocol share** (1 − TCP − UDP), which exposes the Ares Bot protocol-0 fragments. Drop `unique_tcp_window_ratio`. Redefine any "dominant signature" as protocol plus forward/backward packet and payload buckets, without the TCP window. Use Fwd/Bwd Header Length only behind an ablation, because it can also encode OS options.

Destination port is the obvious temptation, especially for brute force on port 22. Destination port alone classifies ten NIDS datasets at 70–100% accuracy, and D'Hooge et al. advise keeping it and all metadata out of models ([D'Hooge et al. 2022](https://www.aminer.org/pub/634d80d090e50fcafd4ebcbc/establishing-the-contaminating-effect-of-metadata-feature-inclusion-in-machine-learned-network)). On CIC-18 the port is also often "wrong" for the label. SSH-Patator started on port 21, SlowHTTPTest hit port 21, and Ares Bot ran entirely on 8080 ([DistriNet](https://intrusion-detection.distrinet-research.be/CNS2022/CSECICIDS2018.html)). The defensible use is a post-hoc **service hint** in the explanation ("login service", "web", "other"). It never enters the classifier, and the team reports the result with and without it. No paper endorses this split explicitly. It is inferred from D'Hooge's exclusion advice and from Flood et al.'s use of port lists only as a diagnostic.

None of these features is benchmarked on 100-flow CIC-18 windows. The recipe is reasoned, not proven, so each addition should survive a leave-one-day-out ablation before it counts.

### Open-set rejection fixes the structural ceiling only if it is calibrated like the test

The rejection rule is simple. Compute the distance from the query to its nearest labelled window in the scaled feature space, and the top-class probability of the soft vote. Answer "Unknown" when the distance exceeds a threshold τ_d **or** the probability is below τ_p. This is the window-level version of the Mahalanobis and distance-to-prototype rules in the out-of-distribution literature ([Lee et al., arXiv 1807.03888](https://arxiv.org/abs/1807.03888v2)). Note what open-set methods achieve on CIC-18 for a held-out class: unknown recall from **35% (SQL injection) to 72% (DDoS)** ([arXiv 2108.09199](https://ar5iv.arxiv.org/html/2108.09199)). Expect to catch some, not all, of the Botnet and Brute Force windows.

The calibration detail decides whether this works. CIC-18 windows from the same day are near-duplicates. A test window from an unseen day is therefore always farther from the reference set than any training window is from its own nearest neighbour. If τ_d is set as the 95th percentile of ordinary nearest-other-window distances, it will be far too tight, and the classifier will answer "Unknown" to most known-family windows too. The `FamilyClassifier` draft in `aegis/family.py` currently does exactly this, with `NearestNeighbors(n_neighbors=2)` over all training windows. Calibrate instead with **leave-one-day-out distances**. For each training window, measure its distance to the nearest window from a *different* day, and take a per-family or pooled quantile of those. Choose τ_p on development days for a target false-Unknown rate on known families, such as ≤10%. This recipe is an inference: no NIDS paper reports plain kNN distance thresholds on window aggregates. It is, however, the only version whose calibration conditions match the test conditions.

### Scoring "Unknown" honestly

The rule must make it impossible to win by abstaining. For a window whose family is **absent from that fold's reference set**, "Unknown" is the correct answer. For a window whose family **is** present, "Unknown" counts as wrong in open-set accuracy and is also reported as an abstention. Publish all of these numbers together:

- open-set accuracy;
- known-family accuracy (closed-set, on families present in training);
- unknown recall (the share of absent-family windows answered "Unknown");
- false-Unknown rate on known families;
- abstention rate, and accuracy on answered windows;
- macro-F1 over the families plus "Unknown".

Always include an "always Unknown" baseline. On seed 0 it would score 12/68 = 18% open-set accuracy and 0% known-family accuracy, which is what an abstention-gaming system looks like. As a reference point, a perfect rejector on top of the current kNN would reach 54/68 = 79%. That is the standard leave-one-attack-out framing in open-set NIDS ([arXiv 2108.09199](https://ar5iv.arxiv.org/html/2108.09199)). It also fits AEGIS's governance: "Unknown" routes to PENDING_REVIEW rather than to a confidently wrong ATT&CK mapping.

## The LLM earns its place as explainer, not judge

The measured result and the literature agree. The LLM should not choose the label. The model that sees the retrieved evidence mostly echoes it and then adds its own errors. Cascade research finds that the cheap model's own confidence (Chow's rule) is hard to beat as the deferral signal ([arXiv 2404.10136](https://arxiv.org/html/2404.10136v1)). The recommended role is **G4, explanation-only**. The classifier's family, its top-3 candidates with probabilities, the "Unknown" reason and the top feature deviations go into the prompt as given facts. The LLM writes the analyst explanation, the ATT&CK-grounded response draft and a severity hint that can only raise severity. This guarantees typing accuracy equals the classifier's while keeping the explainability story.

A reranker mode can be kept behind a flag as an experiment, not a default. It calls the LLM only when the soft-vote margin between the top two families falls below a threshold. The schema enum is restricted to those two families plus "Unknown", so the model cannot invent a family that retrieval never offered. Gemini's twelve "Port Scan" answers show that it does this otherwise, and no CIC-18 test label maps to Port Scan ([benchmark-hybrid-same-network-gemini.json](benchmark-hybrid-same-network-gemini.json)). Adopt the mode only if it wins a paired test on development days. If it is tried, present neighbours as real labelled exemplars with the same feature serialisation, and fix or randomise their order. Example order alone has swung few-shot accuracy from 54% to 93% ([Zhao et al., arXiv 2102.09690](https://arxiv.org/pdf/2102.09690)). Skip chain-of-thought, which helps mainly on math and logic tasks ([Sprague et al., arXiv 2409.12183](https://arxiv.org/abs/2409.12183)).

Structured outputs remove the 19 schema failures. Ollama's `format` field accepts a full JSON Schema and constrains decoding to it. The docs recommend temperature 0, building the schema with Pydantic, and also pasting the schema text into the prompt ([Ollama docs](https://docs.ollama.com/capabilities/structured-outputs); [Ollama blog](https://ollama.com/blog/structured-outputs)). In explanation-only mode, `attack_type` is not a generated field at all. The code writes it from the classifier. A minimal sketch:

```python
class Explanation(BaseModel):
    evidence: list[str]                      # feature-level claims, checkable against the window
    explanation: str
    severity_hint: Literal["LOW", "MEDIUM", "HIGH", "CRITICAL"]
    recommended_actions: list[Literal[...playbook action ids...]]

resp = ollama.chat(model=MODEL, messages=msgs, format=Explanation.model_json_schema(),
                   options={"temperature": 0})
out = Explanation.model_validate_json(resp.message.content)   # one retry on failure, then fallback
```

Log `schema_valid` and count failures as fallbacks rather than dropping them. Constrained JSON tends to help classification-style outputs while hurting free reasoning ([arXiv 2408.02442](https://arxiv.org/html/2408.02442v3)), which is another reason to keep the label out of the LLM. Ollama's logprobs, added in v0.12.11 according to a release-notes mirror ([newreleases.io](https://newreleases.io/project/github/ollama/ollama/release/v0.12.11-rc1)), would allow label scoring and contextual calibration if the reranker is ever used. Verify that against the official release page first.

On model choice, qwen2.5:3b already answered all 137 explanation calls at a median of 2.1 s ([hybrid-evaluation.md](hybrid-evaluation.md)). The Qwen3 report states that its 4B base model beats the larger Qwen2.5-7B on over half of its benchmarks ([arXiv 2505.09388](https://arxiv.org/pdf/2505.09388)). qwen3:4b is a 2.5 GB download and qwen3:8b is 5.2 GB, so both fit in 15 GB of RAM ([Ollama library](https://ollama.com/library/qwen3)). Run qwen3:4b with `think: false` ([Ollama thinking docs](https://docs.ollama.com/capabilities/thinking)) and judge it on explanation faithfulness: the share of explanations with a feature claim that is false for the window. Do not judge it on typing. No benchmark predicts the gain on this task. Fine-tuning is out of proportion to the payoff, since published LoRA and QLoRA results only reach Random Forest parity ([arXiv 2601.15269](https://arxiv.org/abs/2601.15269)).

## Recommended design: features → calibrated classifier → Unknown gate → explaining LLM

The final pipeline keeps detection as it is (the benign-trained Isolation Forest decides "anomalous"). It replaces the naming step with a dedicated family model, which is what `aegis/family.py` already sketches. Its parts are as follows.

**Training data.** Use labelled attack windows (≥50% attack flows) from every usable day-file except the one being judged, capped at about 150 windows per file so no single day dominates. Exclude Infiltration days. Optionally drop windows whose attack flows are mostly zero-payload, which marks them as "Attempted"-style. Use separate sampling seeds for training windows and for evaluation windows.

**Features.** Use the behavioural set above: log1p medians and p90s of payload per packet, backward packet-length std, forward/backward packets and bytes, duration, IAT mean/max, idle and active time, and packet size. Add CVs, the share features (zero-payload, long-flow, SYN/RST/FIN/PSH/ACK, no-response, TCP/UDP/other), the backward/forward byte ratio and the median Down/Up ratio. Leave out Init Fwd Win Bytes, Dst Port, timestamps and IPs.

**Model.** Fit a `RobustScaler` on the training windows. Then soft-vote, 50/50, a `RandomForestClassifier(n_estimators=300, class_weight="balanced", min_samples_leaf=2)` and a `KNeighborsClassifier(k=7, weights="distance")`. Test NCA + kNN and `NearestCentroid(shrink_threshold=…)` as development-only challengers, and keep whichever wins on development days. Fit everything inside each leave-one-day-out fold.

**Unknown gate.** Answer "Unknown" if the top soft-vote probability is below τ_p, or the nearest-incident distance exceeds τ_d. τ_d is the 95th percentile of cross-day nearest-neighbour distances among the training windows. Return `family`, the top-3 `candidates` with probabilities, `novelty_distance`, `novelty_limit`, `unknown_reason`, and a `coarse_group` that reads "Volumetric DoS/DDoS" when those two together exceed τ_p.

**Downstream.** Map the family to ATT&CK through the fixed table, and route "Unknown" to PENDING_REVIEW. Pass the verdict and evidence to the LLM under the explanation schema. Record model version, prompt hash, schema validity and latency in the decision record, as the governance design already does.

The changes should land in this order. Week one covers rank 1 (calibrated Unknown, with the cross-day threshold fix), ranks 3–4 (scaling and soft vote) and the scoring code in `aegis/evaluation.py`. Week two covers the feature ablations (rank 2), label hygiene (rank 7) and the explanation-only LLM with its schema (ranks 8–9). The model swap, NCA and the reranker flag are optional extras. The development harness in `scripts/typing_experiment.py`, with leave-one-day-out, training seed 11 and development-test seed 21, is the right place for all tuning.

## An honest test on windows nobody has looked at

Seed 0 is now development data. It has been inspected several times, and the detector design was fixed after looking at it ([hybrid-evaluation.md](hybrid-evaluation.md)). Arp et al. find data snooping in 57% of top-tier security papers they reviewed ([Arp et al., USENIX Security 2022](https://www.usenix.org/system/files/sec22-arp.pdf)). The protocol below avoids it.

**Freeze before testing.** Freeze the features, τ_p, τ_d, k, the vote weights and the prompt, and record the git commit hash. Only then run the benchmark on **fresh seeds 1–5** across all eight usable day-files, with the reference set always built leave-one-day-out.

**Sample size.** Pooling about 5 × 68 caught windows shrinks the 95% interval from about ±12 to about **±5 points**. Report mean ± SD across seeds as well.

**What to report.** Report every metric from the scoring rules above. Add per-family precision, recall and F1 with support counts, an 8×8 confusion matrix including "Unknown", coarse-group accuracy, and a risk–coverage curve that sweeps τ_p ([arXiv 2108.09199](https://ar5iv.arxiv.org/html/2108.09199)).

**Baselines on the same windows.** Use always-DDoS, the old 14-feature kNN-5 vote, LLM-alone typing, the new classifier closed-set, and the new classifier with the Unknown gate.

**Statistics.** Compare systems pairwise with **exact McNemar tests** on the same windows, which is the recommended test for classifiers compared once on a fixed test set ([Dietterich 1998](https://web.engr.oregonstate.edu/~tgd/publications/dietterich-approximate-statistical-tests-nc1998.pdf)). Add bootstrap CIs on macro-F1 differences ([Raschka](https://sebastianraschka.com/blog/2022/confidence-intervals-for-ml.html)). Windows from the same day are correlated, so a bootstrap that resamples whole day-seed blocks is more honest than resampling single windows. That point is an inference, not a cited standard.

**Ablations.** Run the new classifier without the added features, with the Dst Port hint, and with and without "Attempted"-style windows. As a clearly labelled **optimistic upper bound**, add a within-day time-block split that puts earlier Botnet and Brute Force windows into the reference set. It shows what typing would look like once those families are known in deployment.

## Conclusion

The project's typing problem is less about intelligence than about what counts as a fair question. About a sixth of the "errors" asked the system to name a family it had never seen, and the honest answer was always "I don't know". Once that is scored properly and the classifier gets features that describe attacker behaviour rather than the testbed's TCP stack, the remaining hard case is DoS against DDoS. Without source addresses that split is partly unknowable, so the team should report it as a coarse group rather than tune against noise. For the project narrative, this sharpens the earlier conclusion that the LLM's value lies in explanation. Here it lost 5 windows and won none on the same evidence. So the agentic contribution is a governed hand-off: a measurable classifier names the family or abstains, an "Unknown" goes to a human, and the LLM explains the decision without being able to change it.

The biggest open risk is that the new classifier's improvements are themselves tuned on seen data. The protection is procedural rather than algorithmic: tune on development seeds, freeze the configuration, test once on fresh seeds, and publish the per-family confusion matrix even if the headline number disappoints. An examiner will trust a frozen 70% with an honest abstention rate more than an unfrozen 85%.
