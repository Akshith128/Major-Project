# AEGIS gets governance right, evaluation wrong

AEGIS is built the right way round, but its evidence does not yet back its claims. The architecture follows the 2025 staged-pipeline pattern. Response is recommend-only, high-risk and low-confidence cases go to a human, the LLM never sees labels, payloads or identifiers, and decisions land in a hash-chained audit log. That design lines up well with the EU AI Act's oversight article, the OWASP LLM Top 10 and recent agentic-SOC research. The weak part is the evidence. About ten windows from one day-file, with no machine-learning baseline, no repeated runs and no cost measurement, cannot support any detection claim. The 95% confidence interval on accuracy at n=10 is roughly ±28 percentage points. Published Random Forest and XGBoost models already reach 0.97–0.999 on CSE-CIC-IDS2018, and zero-shot LLMs score near chance on the same data. Two more problems sit underneath. The original CIC-IDS2018 labels contain documented errors, and the features AEGIS relies on most, the TCP initial window and the RST share, are exactly the testbed artefacts the literature warns about. The audit chain shows that records were not edited in the middle. It cannot show who approved them, because operators are not authenticated, and it cannot detect a rewritten or truncated log. Eight must-have changes fix most of this, and nearly all are a few days' work in `aegis/evaluation.py`, `aegis/data.py`, `aegis/audit.py` and `aegis/api.py`. The most important are a Random Forest baseline trained on other day-files, a multi-day evaluation of several hundred windows with MCC and confidence intervals, and HMAC-signed audit entries tied to authenticated users. Once those are in place, the honest claim for the project is "the agentic layer adds explanation, attack typing, governed response and auditability at a measured detection cost". It should not claim "the LLM detects better".

## The governance design already matches what regulators and researchers ask for

The pipeline shape is current. Recent systems coordinate role-specialised agents through either an orchestrator loop or a fixed sequence of stages. CORTEX (2025) uses a four-stage triage pipeline and cut the false-positive rate from **24.9% to 14.2%** compared with a single agent ([arXiv:2510.00311](https://arxiv.org/html/2510.00311v1)). Google's reference agentic SOC uses a root manager agent with human approve/override/pause ([Google Cloud](https://docs.cloud.google.com/architecture/agentic-ai-orchestrate-security-ops-workflows)). AEGIS's linear LangGraph graph (Monitoring → Detection → Risk → Response → Governance) belongs to the staged family. That is a legitimate choice for a student project, because it is deterministic, easy to explain and cheap. The biggest architectural gap is that Detection calls no tools and retrieves no evidence.

The response design is more conservative than the commercial products, and that is a strength. Vendors are moving to "bounded autonomy", where customers decide when automated actions fire ([CrowdStrike](https://www.crowdstrike.com/en-us/press-releases/crowdstrike-delivers-next-breakthrough-in-ai-powered-agentic-cybersecurity-with-charlotte-ai-detection-triage/)). AEGIS never executes anything. OWASP LLM06 (Excessive Agency) names **excessive autonomy** as a root cause and prescribes human approval for high-impact actions ([OWASP LLM06](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)). EU AI Act Article 14(4)(d) requires that overseers can disregard, override or reverse the output ([AI Act Art. 14](https://artificialintelligenceact.eu/article/14/)). AEGIS-GOV-1 does both, and the policy is evaluated in code rather than by the LLM, which matches OWASP's "complete mediation" principle. In the autonomy-level vocabulary of recent SOC literature ([arXiv 2505.23397](https://arxiv.org/abs/2505.23397)), AEGIS is human-in-the-loop for HIGH/CRITICAL, low-confidence and fallback cases, and human-on-the-loop for the rest. That is a sensible place for a first system.

Feeding the LLM only numeric, label-free aggregates is the project's most underrated decision. Log-borne prompt injection against SOC LLMs is now a well-studied attack class. One 2026 study ran **more than 1,100 payloads** across five model configurations and found verdict downgrades in every configuration ([NeurIPS 2026](https://neurips.cc/virtual/2026/168153)). The UK NCSC says prompt injection may never be fully fixed and designs should limit its impact ([NCSC](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection)). AEGIS's `summarize()` passes only shares, ratios and means, never hostnames, payloads or user-agent strings, so attackers have almost no text channel into the prompt. The same choice protects privacy. Gemini's unpaid tier may use prompts to improve Google products, lets human reviewers read them, and states "do not submit sensitive, confidential, or personal information" ([Gemini API terms](https://ai.google.dev/gemini-api/terms)). Several smaller things are also already right. Features and ground truth are kept strictly separate in `aegis/data.py`. `aegis/llm.py` already calls Gemini at `temperature=0` with JSON output, which is half of the "grammar-constrained output" mitigation recommended for unstable LLM classifiers ([arXiv:2510.17883](https://arxiv.org/html/2510.17883v2)). Every decision records whether it came from Gemini or the rule fallback. Comparing the monitoring gate with the full pipeline is the correct way to isolate what the LLM adds. None of the reviewed research papers describe a hash-chained audit trail, so the team can fairly present it as a differentiator. The report should state all of these as deliberate controls, not leave them as implementation details.

## Ten windows from one day-file cannot support a detection claim

The evaluation is where AEGIS falls short of current research practice, and the gap is large. Every serious LLM-IDS paper benchmarks against classical ML. On CSE-CIC-IDS2018, Random Forest and XGBoost reach **0.97–0.999 accuracy** depending on preprocessing ([SHIELD-IDS](https://arxiv.org/pdf/2606.07716); [NEPJOL](https://nepjol.info/index.php/injet/article/view/95492)). Zero-shot GPT-4 on NetFlow CIC-IDS2018 scored **50.25% macro precision**, which is chance, and it was about **7,000× slower** per sample than an RF when the LLM was Llama3-8B ([Houssel et al.](https://arxiv.org/html/2408.04342v1)). Without a baseline on the same windows, a reader cannot tell whether AEGIS is good, trivial or worse than a decision tree. Arp et al.'s widely cited pitfalls paper shows that simple baselines often win on lab data. A 10-second sliding-window packet-count rule beat the KITSUNE autoencoder on Mirai, with AUC **0.998 vs 0.968** ([Arp et al., USENIX Security 2022](https://www.usenix.org/system/files/sec22-arp.pdf)). That example matters for AEGIS, whose monitoring gate is also a window-aggregate rule.

Sample size is the second problem. At n=10 the binomial 95% interval on accuracy is roughly ±28 percentage points. With about five benign windows, a single false positive moves FPR by 20 points, and zero errors out of five still leaves a Wilson interval of roughly 0–43%. Small samples also flatter LLMs in particular. In "From Flows to Words", LLM macro-F1 of about 0.78 on 200 flows fell as the set grew to 2,000 ([arXiv:2510.17883](https://arxiv.org/html/2510.17883v2)). Temperature 0 does not remove run-to-run variance either. Accuracy has been reported to vary by **up to 15%** across identical runs ([arXiv:2408.04667](https://arxiv.org/html/2408.04667v5)), and agentic benchmarks show variance that does not shrink as temperature falls ([arXiv:2602.07150](https://arxiv.org/pdf/2602.07150)). A single run of ten windows is therefore one draw from a wide distribution.

The metric set also needs widening. Chicco and Jurman show that accuracy and F1 "can dangerously show overoptimistic inflated results" on imbalanced data, and recommend MCC, which is high only when all four confusion-matrix cells are good ([PMC6941312](https://pmc.ncbi.nlm.nih.gov/articles/PMC6941312)). Cantone et al. use MCC for the same reason on CIC data ([arXiv:2402.10974](https://arxiv.org/html/2402.10974)). Day-files differ hugely in how many windows are attacks, and spread sampling sets that ratio artificially. Precision is therefore meaningless unless the attack prevalence of each run is reported alongside it (Arp's base-rate fallacy). Operational cost belongs in the results as well. CORTEX reports a median of **152 s and about 23,600 tokens per alert** ([arXiv:2510.00311](https://arxiv.org/html/2510.00311v1)), and LLM-IDS papers routinely report per-sample latency ([arXiv 2507.07413](https://arxiv.org/html/2507.07413v1)). AEGIS currently reports neither.

Finally, the 80-point confidence threshold in AEGIS-GOV-1 is used as if it were calibrated, but it is not. Verbalised LLM confidence is systematically overconfident. GPT-3-class models had average ECE above **0.377**, and even GPT-4's ability to predict its own failures was weak, with an AUROC of about 62.7% ([Xiong et al., ICLR 2024](https://arxiv.org/abs/2306.13063v2)). No framework prescribes a numeric threshold; that choice is left to the organisation's risk appetite. The team must show that "confidence ≥80" actually corresponds to higher accuracy before using it to decide what skips human review. The same confidence also feeds the risk formula with a 0.6 weight.

**What to change in code.** The changes fall into five groups.

- **Baselines.** Add `aegis/baselines.py` with a `RandomForestClassifier` (sklearn, `class_weight="balanced"`) trained per flow on day-files that are *not* in the test set. Map flow predictions to a window verdict with the same ≥50% rule used for ground truth, and record its predictions in each window record next to `gate` and `pipeline`. Add two trivial baselines: majority class, and a single-feature threshold on `unique_tcp_window_ratio`.
- **Metrics.** Extend `confusion()` in `aegis/evaluation.py` with MCC, balanced accuracy, specificity and attack prevalence. Use the gate's continuous score to add ROC-AUC and PR-AUC, and add Wilson or bootstrap 95% CIs (1,000 resamples over windows) for every metric.
- **Paired comparison.** Run McNemar's test on the discordant windows between gate, pipeline and RF. It is the recommended test when classifiers are compared once on a fixed test set ([Dietterich 1998](https://web.engr.oregonstate.edu/~tgd/publications/dietterich-approximate-statistical-tests-nc1998.pdf)).
- **Repeats and stability.** Add a `--repeats` and `--seed` option to the run CLI. Use at least 3 LLM repeats on an identical window set to measure model variance, and at least 5 sampling seeds to measure sampling variance. Report mean ± SD and the per-window verdict flip rate.
- **Calibration and cost.** Pool all escalated windows, bin Gemini's confidence into 5–10 bins, and report a reliability diagram, ECE and Brier score. Log per-agent wall-clock latency and the `usage_metadata` token counts returned by the Gemini SDK. Report median/p95 latency, tokens per window, the escalation rate, the fallback/parse-failure rate and Cohen's kappa between gate and LLM verdicts.

## The dataset and the strongest features carry known artefacts

The original CICFlowMeter files that AEGIS loads have well-documented errors. Liu, Engelen et al. (IEEE CNS 2022) found errors in attack orchestration, feature extraction and labelling of CSE-CIC-IDS2018, and released a corrected, relabelled dataset ([CPS-VO](https://archive.cps-vo.org/node/97449); [DistriNet](https://intrusion-detection.distrinet-research.be/CNS2022/index.html)). Their per-day notes hit AEGIS's features directly. On the FTP-Patator days (14-02 and 16-02), port 21 was closed, so the "attack" flows are RST/ACK replies with no brute force at all. On 23-02, **41.7% of labelled Web Brute Force flows** are mislabelled ([DistriNet CSE-CIC-IDS2018](https://intrusion-detection.distrinet-research.be/CNS2022/CSECICIDS2018.html)). AEGIS's `rst_share` and `no_response_share` will fire strongly on those failed FTP attempts. The pipeline can therefore look accurate while detecting a broken experiment rather than an attack. Most users still rely on the uncorrected releases ([arXiv 2502.06688](https://arxiv.org/pdf/2502.06688)).

The Infiltration days (28-02 and 01-03) are worse. DistriNet calls the original labels "largely unrecoverable", and in its relabelling the real victim–attacker communication on 28-02 is only **44 flows** ([DistriNet](https://intrusion-detection.distrinet-research.be/CNS2022/CSECICIDS2018.html)). Infiltration stays below 50% MCC in every cross-dataset setting ([arXiv:2402.10974](https://arxiv.org/html/2402.10974)). Under AEGIS's ≥50% rule, a 100-flow window from these days mostly measures label noise, not detection.

The features raise a shortcut-learning concern. NIDS datasets let models score **70–100% accuracy from destination port alone** ([arXiv 2502.06688](https://arxiv.org/pdf/2502.06688)). A 2026 preprint reports that a depth-3 tree on initial TCP window size alone reaches AUC 0.985 on CIC-IDS2017 web attacks ([Preprints.org](https://www.preprints.org/manuscript/202610.1120)). That evidence is not peer reviewed and is for the 2017 dataset, so treat it as a warning rather than proof. AEGIS's `SIGNATURE` in `aegis/data.py` includes `Init Fwd Win Bytes`, and its `unique_tcp_window_ratio` is computed from the same column. Both reward a single attack tool on a single OS stack producing identical values, which is a testbed property rather than attack behaviour. Cross-dataset results show how much such scores can fall. Train-on-2018 / test-on-2017 MCC drops from about **96% within-dataset to 26–44%** ([arXiv:2402.10974](https://arxiv.org/html/2402.10974)).

Window construction needs disclosure too. Aggregating "last N flows" is an accepted NIDS technique, but conventions can dominate results. In one 2026 study, the padding choice hid a **67× increase in false alarms** until a leakage-free split was used ([arXiv 2606.11098](https://arxiv.org/abs/2606.11098)). `load_windows()` takes contiguous CSV rows without sorting by Timestamp. In single-attack day-files, attack flows form contiguous blocks, so most windows are 0% or 100% attack and easy to classify.

**What to change in code.** Add a `--labels distrinet` option that loads the DistriNet improved CSE-CIC-IDS2018. Report results with "Attempted" flows counted as benign, and again with them dropped. If time is short, keep the original files and add a "threats to validity" section naming the FTP-Patator, Web-2 and Infiltration problems.

Mark Infiltration day-files with an `excluded_by_default` flag in `list_datasets()` and report them separately. Sort each day-file by `Timestamp` before windowing.

Make the window rule configurable (`label_rule = "majority" | "any" | "mixed_class"`) and run a sensitivity analysis at 10%, 50% and 90%. Also record each window's `attack_share` next to its verdict, so the team can see where errors cluster.

Run an ablation that drops `Init Fwd Win Bytes` from both `SIGNATURE` and the feature set, and report the change in MCC. If performance collapses, the report must say the detector relies on a testbed artefact.

## Detection asks Gemini to do what the literature finds it worst at

The literature is consistent: LLMs are weak classifiers of numeric flow features and strong explainers. In "From Flows to Words", zero-shot Mistral-7B scored **0.09 accuracy** on UNSW-NB15. The best prompted model reached 0.78 macro-F1 on 200 flows, while XGBoost reached **0.953 accuracy**. The authors note that zero-shot prompting "often collapses to a single class" ([arXiv:2510.17883](https://arxiv.org/html/2510.17883v2)). The strongest systems pair the two. IDS-Agent calls ML classifiers as tools ([NeurIPS 2024](https://neurips.cc/virtual/2024/100920)). HuntGPT and the SJSU agentic report system put a Random Forest or ensemble with SHAP in front of the LLM ([arXiv:2309.16021](https://arxiv.org/pdf/2309.16021); [SJSU](https://scholarworks.sjsu.edu/faculty_rsca/7038)). Houssel et al. conclude that LLMs are unfit as standalone NetFlow detectors but promising for explanation and response, and that their explanations contained factual errors and hallucinations ([arXiv 2408.04342](https://arxiv.org/html/2408.04342v1)). AEGIS goes further than a per-flow LLM classifier, because Gemini sees only window-level aggregates. No published zero-shot Gemini number on CIC-IDS2018 exists, so how well this works is an open, measurable question rather than a known failure. AEGIS should test it against an ML detector instead of assuming it.

The recommended restructure keeps the five agents but changes Detection's job. The RF baseline becomes a tool that Detection calls. Gemini receives the RF verdict and probability, the top contributing features (SHAP values or RF feature importances), and the window aggregates. It returns attack type, a MITRE ATT&CK mapping and an analyst-facing explanation. Two guards keep this safe. First, Gemini may raise but never lower the deterministic severity (monotonic escalation). Second, any unknown attack type or response action falls back to rules and PENDING_REVIEW. This keeps the "agentic" story while putting detection on evidence-backed ground. It also makes the team's main result clean: what the LLM adds over gate-only and RF-only on the same windows.

Two further additions bring AEGIS in line with the roles recent systems use. ATT&CK mapping with retrieval roughly doubled accuracy in one small Gemini study, from **about 46% to 78%** on 200 CloudTrail events ([CMC 2026](https://www.sciopen.com/article/10.32604/cmc.2026.077606)). AEGIS's attack-type space is small, so a fixed lookup table (brute force → T1110, DoS/DDoS → T1498/T1499, web/SQLi → T1190, Bot → T1071) is enough, and the same table becomes ground truth for scoring the mapping with micro-F1, as CTIBench does ([arXiv 2406.07599](https://arxiv.org/html/2406.07599v3)). Analyst-feedback memory is the other addition. Microsoft's Phishing Triage Agent updates its reasoning from analyst corrections ([Microsoft](https://www.microsoft.com/en-us/security/blog/2025/03/24/microsoft-unveils-microsoft-security-copilot-agents-and-new-protections-for-ai/)). AEGIS already stores approve/reject notes and could feed the last few into the Detection prompt. Response quality should get a small rubric study: two raters score 30–50 plans for relevance, specificity, proportionality and safety, and report Cohen's kappa. An LLM judge should be used only as a supplement, from a non-Gemini model family, because judges show position, verbosity and self-enhancement bias ([Zheng et al.](https://arxiv.org/html/2306.05685v4)).

In `aegis/llm.py`, add a Gemini `response_schema` for both the Detection and Response JSON, and validate server-side with Pydantic. Enumerate allowed `attack_type` values and playbook actions. Log every parse failure as a fallback event, because output validity is a known failure mode of unguided prompting ([arXiv:2510.17883](https://arxiv.org/html/2510.17883v2)).

## The audit chain proves what was written, not who wrote it

A bare SHA-256 hash chain catches an edit to a record in the middle of the log. It does not catch three other attacks. Anyone who can write the run file can recompute every hash after a change. Deleting the most recent entries leaves a valid chain. And the verify endpoint trusts whatever chain it is given. Classic secure-logging designs therefore add a key: Schneier and Kelsey chain hashes and have the logger authenticate the latest value ([Schneier](https://www.schneier.com/paper-auditlogs.html)). Even those schemes need extra measures against tail truncation ([DBSec 2008](https://dl.ifip.org/index.html/db/conf/dbsec/dbsec2008/MaT08.pdf)). Certificate Transparency goes further, using Merkle trees with signed tree heads and consistency proofs ([RFC 9162](https://www.rfc-editor.org/rfc/rfc9162.html)). OWASP's 2026 agentic guidance asks for tamper-evident, immutable and **signed** audit logs ([Teleport summary of OWASP ASI](https://goteleport.com/blog/owasp-top-10-agentic-applications)). AI Act Article 12 asks for automatic event logging over the system's lifetime ([Mishcon](https://www.mishcon.com/eu-uk-ai-navigator/article-12)), and ISO/IEC 42001 control A.6.2.8 covers AI event logs ([ISMS.online](https://www.isms.online/iso-42001/annex-a-controls/a-6-ai-system-life-cycle/a-6-2-8-ai-system-recording-of-event-logs/)).

The bigger gap is identity. Today an operator types a name and picks a role, so anyone can approve a CRITICAL recommendation as "Senior Analyst". The chain records the claim, not the person. That breaks accountability under NIST CSF 2.0's Roles, Responsibilities and Authorities category (GV.RR) ([Safe Security](https://safe.security/resources/insights/nist-cybersecurity-framework/)) and OWASP ASI03. It also undercuts Article 14, which assumes assigned, competent people do the overseeing. The governance claim of "digital trust" in the project title depends on fixing this.

Three further controls are missing. The first is a stop control. Article 14(4)(e) asks for a "stop" button that halts the system "in a safe state" ([AI Act Art. 14](https://artificialintelligenceact.eu/article/14/)), and OWASP lists kill switches under ASI04 and ASI10. The second is provenance. To reconstruct a decision you need the exact model, prompt and inputs, and Gemini aliases change over time. AEGIS's default `gemini-3.5-flash-lite` is set by an environment variable and not recorded per decision. The third is support against automation bias. Article 14(4)(b) requires overseers to stay aware of it. Microsoft's RCT found analysts agreed more readily with agent "benign" verdicts ([arXiv:2511.13860](https://arxiv.org/html/2511.13860v1)), and a CSA note warns that bulk auto-suppression discards rare true positives ([CSA](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/09/CSA_research_note_ai_soc_alert_noise_20260914-csa-styled.pdf)).

**What to change in code.** The work splits into audit integrity, authentication, decision records and governance controls.

In `aegis/audit.py`:

- Add `hmac.new(key, prev_hash + canonical, sha256)` to each entry. Load the key from an environment variable or OS keyring that is never written to the run directory.
- Add a monotonic `seq` field. After each run, write a signed checkpoint `{run_id, seq, head_hash}` (Ed25519 via `cryptography` is better than HMAC because anyone can verify it) to a separate append-only file or a second location. `verify()` should then report truncation as well as edits.

In `aegis/api.py`:

- Replace name+role sign-in with real authentication: FastAPI OAuth2 password flow with bcrypt-hashed users from a seed file, or OIDC if time allows.
- Enforce roles on the server so only the `analyst` role can call approve/reject.
- Write the authenticated user ID, not a typed name, into each review entry.

In each decision record:

- `model_version` as returned by the API, plus `temperature`.
- `prompt_template_id` and the SHA-256 of the rendered prompt.
- The SHA-256 of the feature vector sent.
- The raw and parsed output, `schema_valid`, `policy_version: "AEGIS-GOV-1.x"`, latency and token counts.

In the governance flow:

- Add a `POST /control/pause` endpoint, and a console button, that stops new runs and forces every decision to PENDING_REVIEW.
- Add a reliability badge in `Governance.tsx` that shows confidence, the fallback flag and a "model rationale, not verified" label next to each recommendation.
- Report governance metrics: review load, auto-approval precision (and the count of benign or wrongly typed windows that were AUTO_APPROVED), escalation recall and override rate. Plot them at several risk thresholds so the 80-point cut-off is justified by a trade-off curve rather than asserted.

Rows 1–4 and 6–8 can be done in parallel by a three-person team in about two weeks. Rows 1 and 3 are mostly scikit-learn and scipy calls. Row 2 is limited mainly by Gemini quota. At 500 windows × 3 repeats, AEGIS makes up to 1,500 detection calls before the gate filters, so cache responses keyed by prompt hash and log token usage to report total cost. A few points remain uncertain. No published Gemini benchmark on CIC-IDS2018 exists, so the window-aggregate LLM detector could do better than per-flow LLM results suggest, and the team should report whatever the numbers show. The TCP-window shortcut evidence is a 2017-dataset preprint. And whether a SOC tool is "high-risk" under the AI Act is unsettled, so Articles 12 and 14 should be presented as a best-practice benchmark rather than a legal obligation.

## Conclusion

The research changes what AEGIS should claim to be. Its value is not that an LLM beats a classifier at spotting DoS floods in lab data; the evidence says it will not. Its value is a governed decision chain. A cheap, verifiable detector produces the verdict. An LLM turns it into an explained, ATT&CK-mapped, proportionate recommendation. A code-enforced policy decides which recommendations a named, authenticated human must sign, and a signed log lets a third party check afterwards who decided what, with which model and on what input. That framing makes the project's existing strengths central rather than incidental: recommend-only response, label-free numeric inputs that shrink prompt injection and privacy exposure, and the fallback provenance flag. It also turns the evaluation gaps into a concrete research question the team can answer with confidence intervals.

One subtler takeaway is that the features making AEGIS's gate look good, initial TCP window homogeneity and RST share, are the same ones that most likely reflect CIC-IDS2018's testbed rather than attacker behaviour. An honest ablation that shows this, and a cross-day test that shows how much performance drops, would make the project more credible to examiners, not less. Most student projects, and many published papers, skip that check ([arXiv:2402.10974](https://arxiv.org/html/2402.10974)).
